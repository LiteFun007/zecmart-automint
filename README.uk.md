# zecmart-automint

Автомінт для ZecMart Launchpad (колекція **ZecPuppets**, 555 шт., free mint).
Node.js ≥ 20, **без жодних зовнішніх залежностей**.

---

## Що я з'ясував про цей мінт (основа всієї архітектури)

**1. Підпис гаманця не потрібен.** Створення ордера — це звичайний
`POST /api/mint/orders` з тілом `{walletAddress, quantity, idempotencyKey}`.
Ні авторизації, ні підпису, ні транзакції. Noir Wallet потрібен лише фронтенду,
щоб узяти адресу. Тому софт працює напряму з HTTP і не залежить від розширення
браузера — це на порядок швидше й надійніше за автоматизацію UI.

**2. Мінт безкоштовний**, тож платіжна гілка (`/payment`, `/verify`,
3 підтвердження в мережі) не задіяна взагалі: один успішний POST = мінт завершено.

**3. Є жорсткий рейт-ліміт по IP — це найдефіцитніший ресурс мінту.**
Ліміт **глобальний на весь API** (не по ендпоінтах) і дуже вузький: кілька
запитів — і все, включно з `/api/mint/orders`, віддає `429 Rate exceeded`.
Відновлення — 15–35 с. Виміряно: 4 ендпоінти по одному запиту з паузами 700 мс
пройшли в першому раунді, у другому все впало в 429.

Наслідок для стратегії: **кожен запит на опитування — це запит, якого не буде
на реальний мінт**. Тому тут бюджетний лімітер замість rps і тиша перед стартом,
а hedged-запити вимкнені за замовчуванням (`maxInFlight: 1`) — зайва паралельна
копія коштує токен і наближає 429.

**4. Бекенд нестабільний.** Замір 24 послідовних запитів без жодного
навантаження:

```
успішних:  67%   (решта — 503 DATABASE_UNAVAILABLE, TIMEOUT, ECONNRESET)
латентність: p50 4.3s   p90 9.1s   max 13.6s
```

Під навантаженням старту буде гірше. Саме тому тут hedged-запити, ідемпотентність
і агресивні ретраї, а не «надіслати запит і чекати».

**5. Відмова «зарано» — швидка.** `409 MINT_NOT_STARTED` повертається за
130–290 мс (перевірка часу спрацьовує до звернення до БД) і несе в тілі
авторитетний `launchAt`. Це робить дешевим підхід «стукати заздалегідь».

**6. Ліміти колекції:** `maxPerWallet: 2`, `maxPerOrder: 2` → один запит на гаманець
з `quantity: 2` вибирає весь ліміт. Більше запитів з тієї ж адреси нічого не дають.

## Як воно працює

| Проблема | Рішення |
|---|---|
| Годинник клієнта ≠ годинник сервера | Синхронізація методом звуження інтервалу по заголовку `Date`: кожна відповідь доводить, що серверний час був у `[S, S+1000)` між відправкою і отриманням. ~24 семпли стискають секундну точність до похибки, що дорівнює найшвидшому RTT. |
| Точність синхронізації обмежена латентністю (±1–2 с) | Старт зсувається раніше автоматично: `-(похибка + 1000 мс)`. Зайвий ранній запит коштує один ретрай, пізній — увесь мінт. |
| Запит зависає на 10+ с | **Hedged requests**: якщо відповіді немає за `hedgeAfterMs`, летить друга й третя копія **того самого** запиту паралельно. Перша реальна відповідь виграє. |
| Дубль-копії можуть створити два ордери | **Один idempotency-key на гаманець на весь запуск** (і він зберігається на диск). Повтор із тим самим ключем повертає вже створений ордер, а не новий. |
| Таймаут: запит міг долетіти, а міг ні | Класифікується окремо як `INDETERMINATE` → повтор із тим самим ключем. Ніколи не спалює другий слот із ліміту 2. |
| 503 / HTML-сторінка помилки від CDN | Класифікатор не падає на не-JSON тілі, вважає це транзієнтом і відступає з експоненційним backoff. |
| Невідомий код помилки | За замовчуванням **ретрай**, а не відмова. Гаманець «списується» лише на явних `SOLD_OUT` / ліміт / некоректна адреса. |
| Час старту зсунули | `launchAt` перечитується під час очікування і береться з тіла кожної відмови `MINT_NOT_STARTED`. Розклад переобчислюється на льоту. |
| Процес впав посеред мінту | Кожна зміна стану синхронно пишеться й fsync-иться в `state/orders.json`. Після перезапуску ключі ідемпотентності підхоплюються. |
| DNS / TLS на критичному шляху | IP резолвиться один раз наперед, пул keep-alive з'єднань прогрівається до старту і ще раз за 3 с до нього. |
| Рейт-ліміт по IP з'їсть мінт | Token bucket відкалібрований під **вікно сервера**, а не під бажану швидкість: `windowBudget` запитів на `windowMs`. Ємність = бюджет вікна, тож тиша накопичує токени. |
| Підготовка перед стартом спалить бюджет | **Тиша за 45 с до T0**: синхронізація годинника й прогрів з'єднань робляться за 2.5 хв до старту, далі — жодного запиту, щоб бюджет відновився на повну. Сокети тримаються TCP keep-alive без HTTP-пінгів. |
| Сервер почав віддавати 429 | Після 5 відповідей 429 софт сам знижує темп і вимикає паралельні копії. |
| `setTimeout` промахується на десятки мс | Останні 25 мс до старту — активне очікування через `setImmediate`. |

Кожна адреса — незалежний воркер. Падіння або бан одного гаманця не впливає на решту.

## Налаштування

```bash
cd ~/nftmintsoft
```

Впиши адреси в `wallets.txt` — по одній на рядок (`#` — коментар):

```
t1YourFirstAddress...
t1YourSecondAddress...
```

Адреси мають бути **реальні, з гаманців, до яких ти маєш доступ** — саме на них
запишеться власність у базі ZecMart.

---

## Запуск

> **Не запускай `--recon` і `--rehearse` в останні ~10 хвилин перед стартом.**
> Кожен прогін витрачає бюджет запитів по IP, а він потрібен цілим саме о T0.

Розвідка: стан колекції, час до старту, ліміти по кожному гаманцю.
```bash
node index.js --recon
```

Репетиція — проганяє справжній бойовий шлях запиту (сервер має відповісти
`MINT_NOT_STARTED`). Відмовляється працювати, якщо мінт уже стартував.
```bash
node index.js --rehearse
```

Бойовий запуск. Чекає до `launchAt`, тримає з'єднання гарячими й б'є в момент старту.
**Запускати за 5–10 хвилин до старту.**
```bash
node index.js
```

З детальним логом кожної спроби:
```bash
node index.js --debug
```

Якщо мінт уже відкрито і треба бити негайно:
```bash
node index.js --now
```

Доперевірити статус створених ордерів (можна запускати скільки завгодно разів):
```bash
node index.js --reconcile
```

## Тюнінг (`config.json`)

| Параметр | Сенс |
|---|---|
| `timing.leadMs` | Наскільки раніше за `launchAt` починати (від'ємне). Автоматично зсувається ще раніше на величину похибки годинника. |
| `timing.hedgeAfterMs` | Через скільки без відповіді слати паралельну копію. Менше = агресивніше й більше навантаження. |
| `timing.maxInFlight` | Максимум одночасних копій одного запиту на гаманець. |
| `timing.hotRetryMs` | Пауза між спробами у «гарячому» вікні після старту. |
| `timing.hotWindowMs` | Тривалість гарячого вікна. |
| `network.requestTimeoutMs` | 12 с — підібрано під p90 ≈ 9 с. Менше = більше марних обривів. |
| `network.windowBudget` / `windowMs` | Бюджет запитів на вікно (за замовчуванням 6 на 30 с ≈ 0.2 rps). **Піднімати не варто** — заміряний ліміт сервера десь тут і є. |
| `timing.quietBeforeMs` | Скільки секунд перед стартом не слати нічого взагалі. |
| `timing.preOpenMs` | За скільки до старту робити фінальну підготовку (має бути помітно більше за `quietBeforeMs`). |
| `behaviour.stopOnSoldOut` | Зупиняти всі воркери, щойно сервер сказав sold out. |

## Результат

- `state/orders.json` — актуальний стан по кожному гаманцю (`ORDERED` → `CONFIRMED`).
- `state/run-*.ndjson` — повний машиночитний лог запуску.

Підсумок друкується в кінці: `confirmed / ordered / limit / failed`.

## Обмеження, про які варто знати

- **Тільки безкоштовний мінт.** Якщо ціну зроблять ненульовою, софт це помітить,
  голосно попередить і не платитиме: платіж вимагає підписаної ZEC-транзакції
  з гаманця, і робити це автоматично небезпечно.
- **Ідемпотентність — припущення.** Фронтенд шле `x-idempotency-key`, тож сервер
  майже напевно її реалізує, але перевірити ззовні неможливо. Якщо ні — найгірше,
  що станеться: другий ордер упреться в ліміт 2 на гаманець.
- **Кілька гаманців обходять правило «2 на гаманець» за духом**, хоч технічно це
  дозволено API. Проєкт може потім відсіяти такі адреси — ризик на тобі.
- **Це не NFT у блокчейні.** `assetNetwork: "database"` — власність існує лише
  в базі ZecMart. Жодного ZSA-токена в Zcash не випускається.
